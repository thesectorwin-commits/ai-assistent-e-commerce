# AI-ассистент — контекст проекта

AI-ассистент на маркетплейсе (витрина + чат).

## Структура проекта

```
index.html       — вся витрина + чат, один файл (vanilla JS, без фреймворков)
api/chat.js       — основной диалоговый LLM-эндпоинт (OpenAI, structured outputs)
api/extract.js    — dynamic slot filling: извлекает параметры подбора из свободного текста
api/transcribe.js — голосовой ввод для Safari/iOS (Whisper, т.к. Web Speech API там нет)
package.json      — зависимости (openai SDK)
README.md         — инструкция по деплою на Vercel
```

`index.html` НЕ обычный фрагмент — у него полноценный `<!DOCTYPE html><html><head>` с
`<meta name="viewport">`. Это важно: без явного viewport мобильные браузеры рендерят
страницу как десктопную (~980px) и уменьшают масштаб — уже ловили этот баг один раз.

## Архитектура ассистента — три слоя

1. **Скриптовый slot-filling (бесплатно, без LLM).** Категории лыжи/наушники/подарок
   описаны декларативно в `CATEGORY_SCHEMAS` (intro + questions + after) — единый движок
   `startCategoryFlow`/`askFlowQuestion`/`handleFlowAnswer`, а не отдельные bespoke-функции
   на каждую категорию. Добавить простую 2-вопросную категорию = добавить запись в таблицу.
   Экипировка для лыж дополнительно имеет вложенный под-подбор по типу снаряжения
   (`EQUIP_PARAMS`/`PARAM_DEFS`/`BUDGET_RANGES`) — тоже декларативно.
   Короткие сообщения (≤4 слов) матчатся как «команды» через keyword-регексы
   (`EQUIP_KEYWORDS`, `parseColorWord`, `parseShoeSize`).

2. **RAG-поиск (retrieval).** TF-IDF с нуля на vanilla JS (токенизация со стоп-словами →
   IDF → косинусная близость). Для всего, что не попадает в 3 сценария, или для
   follow-up-вопросов без явного упоминания товара — с фолбэком на `lastShownIds` +
   текущую категорию (с учётом уже применённых hard-фильтров).

3. **Генерация LLM поверх retrieval-кандидатов.** Модель никогда не видит весь каталог —
   только shortlist (5 карточек с ценой/скидкой/рейтингом/остатком/специфика).

### Пайплайн подбора — формально

Каждый ход (что скриптовый equip-флоу, что свободный текст через `handleLongTail`) идёт
строго через эти стадии, и ни одна стадия не пропускается и не переставляется:

```
Intent extraction → Hard filters → Candidate retrieval → Candidate validation → Ranking → LLM explanation
```

1. **Intent extraction** — из текста или чипов достаём category/equip/budget/size/color
   (`parseBudgetCeiling`, `parseShoeSize`, `parseColorWord`, `/api/extract` для длинных
   сообщений).
2. **Hard filters** — `applyKnownFilters` (скриптовый флоу) или budget/size/color-ветки в
   `handleLongTail` (свободный текст) режут пул детерминированно, БЕЗ участия LLM. Каждая
   стадия строго сужает предыдущую — никогда не откатывается на более широкий пул, когда
   ничего не подошло (это и есть P0-1/P0-2: раньше было наоборот).
3. **Candidate retrieval** — TF-IDF (`ragRetrieve`) для свободного текста поверх уже
   отфильтрованного (или ещё не отфильтрованного при первом заходе) пула.
4. **Candidate validation** — сервер (`api/chat.js`) независимо перепроверяет ответ модели:
   (a) `id` обязан быть в `candidateIds`, присланных в ЭТОМ запросе (whitelist, fail-closed);
   (b) если присланы `candidates`+`constraints` — сервер сам, по реальным данным кандидата
   (price/colors/sizeRange), проверяет, что выбранный id не нарушает известный бюджет/размер/
   цвет, и молча вырезает его из ответа, даже если id прошёл whitelist. Модель никогда сама
   не является source of truth по соответствию жёстким ограничениям — она может НЕ выбрать
   то, что не подходит, но финальную проверку делает код, не она.
5. **Ranking** — среди того, что прошло validation, модель (или `rankSki`/rating-сортировка
   в скриптовом флоу) выбирает, что показать первым/что процитировать.
6. **LLM explanation** — модель размечает выбранные id тегами `reasons` (`price`/`discount`/
   `rating`/`delivery`/`stock`/`color`/`size`/`specs`/…) — **не пишет текст сама**. Текст
   «Почему подобрали» собирается детерминированно на клиенте (`buildWhyText`/`reasonText`
   в `index.html`) из реальных полей товара — у модели физически нет способа протащить
   несуществующий факт в этот текст.

### Ключевые принципы, которых стоит держаться при доработках

- **LLM — мозг диалога, не источник истины для каталога и не источник истины по хардфильтрам.**
  Цена/наличие/скидка рендерятся из данных карточки. Соответствие бюджету/размеру/цвету
  проверяется кодом (клиент + сервер), а не текстом модели.
- **Hard vs soft фильтры.** Размер обуви/бюджет/цвет — жёсткие (исключают товар, каждая
  стадия только сужает пул, никогда не расширяет обратно). Рост/вес/стиль катания — мягкие
  сигналы ранжирования (влияют на relevance, не исключают).
- **"Ничего не найдено" — отдельное явное состояние**, а не молчаливый фолбэк на
  неподходящие товары. И в скриптовом флоу (`showEquipResults`), и в `handleLongTail`
  пустой результат после хардфильтров рендерится как честное сообщение + явный chip
  «убрать одно ограничение» (`chipKind:'relax'`/`'budgetRelax'`) — товары, нарушающие
  ограничение, показываются только по явному клику пользователя, никогда автоматически.
  Это отдельное состояние от «retrieval ничего не нашёл по смыслу» и от «LLM недоступна» —
  у каждого свой текст, их нельзя путать.
- **Structured state вместо голой истории.** `dState.currentProduct` (entity resolution для
  «этот»/«него») и `dState.exclusions` (негативные предпочтения типа «только не белые»)
  передаются модели явным JSON-блоком «Состояние диалога» в каждом запросе.
- **Dynamic slot filling — только когда оправдано.** Извлечение параметров из свободного
  текста (`/api/extract`) запускается ТОЛЬКО если сообщение длинное, упоминает категорию
  И содержит цифру/явный уровень — иначе это удорожило бы каждое простое сообщение лишним
  LLM-вызовом. См. `tryDynamicSlotFill` в `index.html`.
- **Никогда не даём модели выдумывать характеристики** вне поля `specs` кандидата — явно
  прописано в `LLM_INSTRUCTIONS`.
- **Один-единственный budget boundary semantics.** «До X» / «не дороже X» = `price <= X`
  проходит, `price > X` — нарушение. Раньше `knownBudget` (структурный диапазон из
  `state.known.budget`) и `budgetMax` (потолок из свободного текста) проверялись двумя
  разными выражениями (`>=` vs `>`), из-за чего товар ровно по верхней границе бюджета
  иногда неверно отбраковывался. Обе проверки в `api/chat.js` теперь идут через один
  `exceedsBudget(price, max)` (`api/_budget.js`) — новую границу заводить только там, не
  копировать сравнение inline второй раз. Тест: `scripts/budget_boundary.test.js`.
- **`reasons` — тоже проверяются на данных, не только `id`.** Каждый тег в `items[].reasons`
  должен подтверждаться реальным полем кандидата (`discount`/`stock`/`rating`/`specs` и
  т.п.) и, для `price`/`size`/`color`, ещё и тем, что соответствующее ограничение вообще
  было заявлено в этом ходе (`reasonIsEvidenced` в `api/chat.js`). Тег без данных для
  подтверждения молча вырезается — так же fail-closed, как whitelist для `id`.
- **Reply ↔ items: соответствие пока не обеспечено кодом, только по конвенции prompt'а.**
  Если `reply` называет конкретный товар как рекомендацию, его id обязан быть в `items`;
  остальные id в `items` должны быть тем, что `reply` реально обсуждает (сравнение,
  альтернатива, дополнение) — не кандидатом, добавленным "просто потому что он был в
  списке". Разрыв нашёлся на TC-30 (E2E раунд 2): `items` включал второй товар, ни разу не
  упомянутый в `reply`. Сознательно НЕ стали чинить это детерминированной серверной
  проверкой (сопоставление имени товара с текстом `reply`) — опробованный вариант ломает
  уже рабочие ответы вида «Вот подходящий вариант:» без явного названия (TC-24), то есть
  сам создаёт новый разрыв reply/items вместо того, что чинил. Если возьмётесь чинить это
  по-настоящему — это отдельная, более крупная задача (нужно что-то вроде извлечения
  упомянутых сущностей из `reply`), не точечная правка.
