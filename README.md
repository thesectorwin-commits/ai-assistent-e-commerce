# AI-ассистент — деплой и API-контракт

Витрина маркетплейса + AI-чат-ассистент подбора товаров. Frontend — один файл
`index.html` (vanilla JS, без сборки). Backend — три serverless-функции на Vercel
(`api/chat.js`, `api/extract.js`, `api/transcribe.js`), которые держат ключ OpenAI на
сервере и никогда не отдают его клиенту.

Ключ никогда не попадает в браузер — фронтенд стучится в `/api/chat` (и `/api/extract`,
`/api/transcribe`) на том же домене, относительным путём. Убедиться в этом можно прямо в
исходнике: в `index.html` ищите `fetch(route || '/api/chat', ...)` — это единственное
место, откуда фронтенд обращается к LLM-бэкенду.

---

## API-контракт

Все три endpoint'а — обычные Vercel serverless-функции (`export default async function
handler(req, res)`), без фреймворка. Общее для всех:
- Только `POST` — любой другой метод (`GET`, `OPTIONS`, ...) → `405 {"error":"Method not
  allowed"}`.
- Тело запроса — обычный JSON, `Content-Type: application/json`.
- Каждый ответ несёт заголовок `X-Request-Id` (и то же значение — в теле любого ответа с
  ошибкой) для трассировки одного вызова по логам.
- CORS не настроен — заголовки `Access-Control-Allow-Origin` не возвращаются, `OPTIONS`
  не обрабатывается отдельно (упадёт в общий `405`). Значит: вызовы с сервера (curl,
  Python/Node HTTP-клиент) работают без ограничений; вызов через `fetch`/`XHR` из браузера
  со стороннего origin будет заблокирован политикой CORS самим браузером.
- Rate limit — **best-effort**, in-memory, ~20 запросов/мин на IP, отдельный счётчик на
  каждый endpoint. Это НЕ жёсткая гарантия: Vercel serverless-инстансы не обязаны делить
  память между вызовами (cold start = новый процесс, трафик может уйти на другой
  инстанс/регион) — но для одного «горячего» инстанса ограничение реально работает и
  проверяемо (см. curl-пример ниже). Ответ при превышении: `429 {"error":"Too many
  requests, slow down"}`.
- Таймаут апстрима — 20 сек (15 сек для `/api/extract`) → `504 {"error":"Upstream ...
  timed out"}` вместо зависания.
- Аутентификация со стороны вызывающего **не требуется** — эндпоинты полностью открытые.
  `OPENAI_API_KEY` используется только сервером для звонка в OpenAI, клиент его никогда
  не передаёт и не видит.

### `POST /api/chat` — основной диалоговый эндпоинт

Request body:
```json
{
  "messages": [
    {"role": "user", "content": "строка, до 8000 символов на сообщение"},
    {"role": "assistant", "content": "..."}
  ],
  "candidateIds": ["s1", "he2"]
}
```
- `messages` — обязателен. Массив 1–40 элементов, `role` строго `"user"` или
  `"assistant"` (без `"system"` — системный промпт передаётся первым `user`-сообщением
  на стороне фронтенда). Суммарная длина всех `content` — не более 24000 символов
  (`400 {"error":"Conversation history too large"}` при превышении), помимо лимита на
  каждое отдельное сообщение.
- `candidateIds` — **опционален по схеме, но обязателен по факту**, если вы хотите
  увидеть непустой `items` в ответе. Это whitelist ID товаров, которые действительно
  разрешено порекомендовать в этом ходе диалога. Если поле не передано — сервер тем не
  менее ответит `200`, но `items` в ответе гарантированно будет пустым: это **fail-closed**
  защита от галлюцинаций (см. "Архитектурные заметки" ниже), а не баг. Если передано —
  массив строк, максимум 20 элементов, каждая строка ≤ 60 символов, иначе `400
  {"error":"Invalid candidateIds payload"}`.

Response `200`:
```json
{
  "reply": "Текст ответа ассистента, 1-2 предложения на русском",
  "items": [
    {"id": "s1", "why": "рост 185, чёрный цвет, для скорости"}
  ]
}
```
`items` — массив 0–3 элементов, каждый `id` гарантированно принадлежит переданному
`candidateIds` (сервер сам фильтрует ответ модели против этого списка перед отправкой —
клиентский фильтр в `index.html` дублирует ту же проверку, но не является единственной
защитой).

Ошибки:
| Код | Когда |
|---|---|
| 400 | `messages` отсутствует/пустой/>40 элементов/неверная форма сообщения/суммарно >24000 символов; `candidateIds` не массив строк или >20 элементов |
| 405 | метод не `POST` |
| 429 | rate limit (см. выше) |
| 502 | модель не вернула ответ, вернула невалидный JSON, либо сетевая ошибка (не таймаут) до OpenAI |
| 504 | таймаут запроса к OpenAI (20 сек) |

### `POST /api/extract` — динамическое извлечение параметров подбора

Используется фронтендом только для сценария «экипировка для горных лыж», когда
сообщение похоже на прямую формулировку параметров («рост 185, вес 78, бюджет 40к»).

Request body:
```json
{"messages": [{"role": "user", "content": "рост 185, вес 78, хочу лыжи для новичка"}]}
```
- До 10 сообщений, ≤2000 символов каждое, ≤6000 символов суммарно. Нет `candidateIds` —
  это чистое извлечение сущностей, а не рекомендация товаров.

Response `200` (форма гарантирована схемой, конкретные значения — результат работы LLM,
поэтому недетерминированы; пример ниже снят с живого деплоя для этого же запроса):
```json
{"category":"лыжи","style":"mid","height_cm":185,"weight_kg":78,"shoesize":null,"budget_max":null,"color":null}
```
Все поля — `string|number|null`; `category` ограничена enum'ом
`лыжи|ботинки|палки|шлем|маска|null`, `style` — `beg|mid|adv|null` (модель сама решает,
что считать «начинающим» — не ждите точного соответствия ключевым словам сообщения).
Коды ошибок те же 400/405/429/502/504, что и у `/api/chat`.

### `POST /api/transcribe` — расшифровка голосового сообщения (Whisper)

Request body:
```json
{"audio": "<base64 без префикса data:>", "mimeType": "audio/webm"}
```
- `audio` обязателен, ≤3 000 000 символов base64 (~2.25 МБ бинарных данных — с запасом
  под лимит тела запроса Vercel в 4.5 МБ).

Response `200`: `{"text": "распознанный текст"}`. Коды ошибок те же 400/405/429/502/504.

## Проверка на живом деплое: работает ли `/api/chat` "по-настоящему"

Да. Быстрая проверка без ключа (ключ не нужен — он серверный). **На Windows держите JSON
в одну строку** без буквальных переносов строк внутри `-d '...'` — многострочный `-d` в
Git Bash/cmd на Windows иногда портит кодировку кириллицы на пути к серверу (сам сервер
тут ни при чём, проверено — то же тело через файл с явной UTF-8 кодировкой доходит
корректно):

```bash
curl -s -X POST "домен/api/chat" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"Кандидаты: [{\"id\":\"s1\",\"name\":\"Atomic Vantage 76 CTI\",\"price\":19990}]. Сообщение покупателя: хочу лыжи Atomic Vantage, подойдут?"}],"candidateIds":["s1"]}'
```

Ожидаемый ответ — реальный текст от модели плюс карточка `s1` с полем `why` (не
статичная заглушка). Пример живого ответа (снят непосредственно с прод-деплоя,
дословно, без правок):
```json
{"reply":"Atomic Vantage 76 CTI – это лыжи, предназначенные как для начинающих, так и для опытных лыжников...","items":[{"id":"s1","why":"Подходят для катания на подготовленных склонах и обладают хорошей маневренностью."}]}
```

Проверка без `candidateIds` (должно вернуться `items: []`, а не список без ограничений —
это доказывает, что server-side whitelist реально работает, а не просто транслирует
ответ модели):
```bash
curl -s -X POST "домен/api/chat" \
  -H "Content-Type: application/json" \
  -d '{"messages":[{"role":"user","content":"хочу лыжи Atomic Vantage"}]}'
```

Проверка rate limit (после ~18-20 быстрых запросов подряд начнутся `429`):
```bash
for i in $(seq 1 25); do
  curl -s -o /dev/null -w "%{http_code} " -X POST "домен/api/chat" \
    -H "Content-Type: application/json" -d '{"messages":[{"role":"user","content":"hi"}]}'
done
```

## Архитектурные заметки (важно для честного E2E-тестирования)

- **LLM никогда не видит весь каталог.** Фронтенд сам делает TF-IDF retrieval по всей
  базе товаров и присылает в `messages` только узкий shortlist кандидатов (обычно ≤5-15)
  для конкретного сообщения — модель может рекомендовать только из них.
- **`candidateIds` — это whitelist, который сервер проверяет сам**, а не просто
  прокидывает ответ модели клиенту (см. код `api/chat.js`, блок `parsed.items =
  parsed.items.filter(...)`). Если тестируете эндпоинт напрямую (не через UI), обязательно
  передавайте `candidateIds`, иначе `items` всегда будет пустым — это ожидаемое
  fail-closed поведение, не баг сервера.
- **Cross-sell** («что ещё купить к лыжам», рекомендации в корзине) — гибридная схема:
  сначала детерминированная таблица `COMPLEMENT_RULES` в `index.html` сужает весь каталог
  до реально релевантных кандидатов, и только затем (если доступна) LLM выбирает из НИХ
  и объясняет — модель не может изобрести совместимость сама.
- **Entity resolution** («этот», «второй», «у него») разрешается на фронтенде через
  `dState.currentProduct`, который явным JSON-блоком «Состояние диалога» передаётся модели
  в каждом сообщении — это не magic, это структурированное состояние в `messages[].content`.
- Бизнес-логика подбора (RAG, retrieval, entity resolution, cross-sell, guardrails от
  галлюцинаций) целиком живёт в `index.html` (frontend) — сами API-эндпоинты в `api/*.js`
  тонкие: валидация + вызов OpenAI + whitelist-фильтрация ответа. Если тестируете именно
  «AI-ассистента» как систему, а не изолированный HTTP-контракт, тестируйте через UI —
  прямые вызовы `/api/chat` без точного повторения формата `messages`/`candidateIds`,
  которые формирует фронтенд, дадут пустые/нерелевантные ответы не потому что бэкенд
  сломан, а потому что вы не воспроизвели то, что реально шлёт браузер.

## Переменные окружения

| Переменная | Обязательна | Назначение | По умолчанию |
|---|---|---|---|
| `OPENAI_API_KEY` | **Да** | Ключ OpenAI, читается сервером (`new OpenAI()`) для всех трёх эндпоинтов | — (без него любой вызов упадёт в `502`) |
| `OPENAI_MODEL` | Нет | Модель для `/api/chat` и `/api/extract` | `gpt-4o-mini` |
| `OPENAI_TRANSCRIBE_MODEL` | Нет | Модель для `/api/transcribe` | `whisper-1` |

Локально — скопируйте `.env.example` в `.env` и подставьте свой ключ:
```bash
cp .env.example .env
# .env.example содержит только placeholder:
# OPENAI_API_KEY=sk-...
```
**Настоящий ключ никогда не коммитится** — `.env` в `.gitignore`, в этом репозитории и
архиве присутствует только `.env.example` с плейсхолдером.

## Локальный запуск (Vercel CLI)

```bash
npm install
vercel dev
```
`vercel dev` поднимет и статику (`index.html`), и `api/*.js` на `http://localhost:3000`
(порт может отличаться — смотрите вывод команды), подхватив переменные окружения из
`.env` в этой же папке. Без `OPENAI_API_KEY` в `.env` эндпоинты будут отвечать `502
Upstream model error` при любом реальном вызове модели.

## Деплой на Vercel (с нуля)

1. `npm i -g vercel` (один раз)
2. Из этой папки: `vercel`, затем `vercel --prod` для продакшен-ссылки — либо запушьте
   папку в GitHub и импортируйте репозиторий на vercel.com (zero-config: статика + `api/`
   определяются автоматически, `vercel.json` не требуется).
3. Vercel Dashboard → Settings → Environment Variables → добавьте `OPENAI_API_KEY`
   (обязательно) и опционально `OPENAI_MODEL`/`OPENAI_TRANSCRIBE_MODEL`.
4. Redeploy.

### Важно: это открытый ключ на сервере, не приватный стенд

Любой посетитель ссылки может писать в чат и тратить ваш OpenAI-баланс — эндпоинты не
защищены авторизацией сверх rate limit'а. Для демо это обычно некритично, но если
раздаёте ссылку шире:
- поставьте лимит расходов на ключ в биллинге OpenAI (Settings → Limits);
- либо добавьте проверку заголовка/пароля в `api/*.js`.

## Модель

По умолчанию `gpt-4o-mini` — быстрая и дешёвая, подходит для чат-подбора товаров и
structured outputs. Для более качественных ответов задайте `OPENAI_MODEL=gpt-4o` в
переменных окружения, без правки кода.
